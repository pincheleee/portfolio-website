I Built a FERPA-Compliant SARB Tracker in 3 Days

California schools are legally required to document a chain of interventions before referring chronically absent students to the Student Attendance Review Board (SARB). Truancy letters, parent contacts, SART meetings, attendance thresholds -- all of it has to be tracked, proven, and packaged into a LACOE-compliant referral packet.

Right now, most schools do this with scattered spreadsheets, filing cabinets, and institutional memory. When staff turn over, evidence gets lost. When SARB day comes, admins scramble to assemble packets from three different systems. I built a tool to fix that.

What It Does

SARB Tracker reads attendance data directly from Aeries (the student information system my district uses), tracks intervention evidence in a sidecar database, and generates 7-page LACOE-format referral packets as PDFs. It also runs a scheduled weekly reporter that outputs an action list telling admins which students are ready for referral and which still need evidence.

The key architectural decision: Aeries is strictly read-only. The app never writes back to the district's student database. All intervention evidence (letters, contacts, SART meetings) lives in its own isolated sidecar. This is both a safety boundary and a FERPA boundary -- the fewer systems that write student data, the smaller the compliance surface.

The FERPA-First Architecture

Every feature was designed around data minimization and auditability:

  • Immutable audit logging: Every single read of student data writes a row to the audit log. Who accessed what, when, from which request, and whether it was disclosed to a third party.
  • Pydantic allowlists: All API response models use extra="forbid". If a field isn't explicitly in the schema, it can't leak. No accidental PII exposure through overly broad serialization.
  • Dual database isolation: The Aeries connection is physically separate from the sidecar connection. Different engines, different connection strings, different access patterns. You can't accidentally write to Aeries even if you try.
  • Report-only pilot: For the initial rollout, the app doesn't even run as a web server for staff. It reads a restricted Google Sheet (where admins log evidence) and Aeries, then drops a CSV into a restricted Drive folder. Minimal access surface.
The Google Sheet is keyed by school_code + student_id only. No fuzzy matching. No student names in the Sheet at all. Names only appear in the final report output, which lives in a restricted folder accessible only to authorized SARB staff.

Classification Engine

California Education Code defines specific thresholds that trigger legal notification requirements. The classification engine implements these with a strict priority order:

  • Chronic truant: 10%+ unexcused absences -- immediate SARB referral territory
  • Truant: 3+ unexcused absences -- legal notification trigger (Ed Code 48260)
  • Chronic absentee: 10%+ total absences -- intervention required
  • At risk: 5-9.9% total absences -- early warning
  • Clean: Below 5% -- no action

Unexcused-based tiers always take priority over total-absence tiers because they trigger legal referral actions. A student with 14% total absences AND 4 unexcused days gets classified as truant, not chronic_absentee, because the legal obligation is more urgent.

The Stack

  • Backend: Python 3.11, FastAPI, SQLAlchemy (dual engines)
  • PDF generation: Jinja2 + WeasyPrint for LACOE 7-page packets
  • Auth: Google OIDC JWT verification with JWKS
  • Google integration: Sheets API (read evidence) + Drive API (write reports) via service account
  • Observability: Prometheus metrics + structured JSON logging with request_id threading
  • Typing: mypy --strict across the entire codebase, zero suppressions
  • Deployment: Docker + docker-compose (MSSQL for Aeries, SQLite sidecar), systemd timer for scheduled reports
  • MCP: FastMCP server for AI assistant integration

39 tests, strict typing, clean linting. The whole thing was built in 3 days across multiple AI-assisted coding sessions -- but every architectural decision was deliberate and rooted in the compliance requirements of working with minor student data.

What's Next

The code is done. What's left is credential setup and a small-group pilot:

  • Create the Google service account and restricted Sheet/folder
  • Get Aeries API credentials from district IT
  • Run the first real report against staging data
  • Pilot with the small SARB admin team before broadening access

After that, the product direction is clear: this is a tool that any California district using Aeries could use. There are over 1,000 districts on Aeries in the state, and SARB compliance is a universal pain point. The architecture was designed from day one to be multi-tenant -- school code isolation, configurable API endpoints, district-scoped service accounts.
