Building a FERPA-Compliant SARB Tracker From Scratch

I'm building a tool to solve a problem I watch happen every year at my district: when it's time to refer chronically absent students to the Student Attendance Review Board (SARB), admins scramble to assemble evidence from three different systems, filing cabinets, and institutional memory. California Ed Code requires a documented chain of interventions before referral -- truancy letters, parent contacts, SART meetings -- and right now that trail lives in scattered spreadsheets and people's heads.

This is a build-in-public post. The architecture is done, the tests pass, but this project has never touched real student data yet. Here's what's working, what's stubbed, and what's next.

The Architecture

The core design decision was treating this as two isolated databases from day one:

  • Aeries (read-only): The district's student information system. SARB Tracker reads attendance counts and student profiles but never writes back. This is enforced at the engine level -- separate SQLAlchemy connections with different access patterns.
  • Sidecar (read/write): Where intervention evidence lives. Letters sent, contact attempts, SART meetings, and an immutable audit log.

This separation isn't just good engineering -- it's a FERPA boundary. The fewer systems that write student data, the smaller the compliance surface. The app can be blown away and rebuilt without affecting the district's source of truth.

What Actually Works Today

  • Attendance classification: Five tiers (clean through chronic truant) with California Ed Code priority ordering. Unexcused-based tiers rank higher than total-absence tiers because they trigger legal notification requirements. Fully tested.
  • PDF packet generation: 7-page LACOE-format SARB referral packets rendered with Jinja2 + WeasyPrint. Cover sheet, attendance records, truancy letters, contact log, SART notes, interventions summary, signature page. Tested with page-count assertions.
  • Case tracking: Admin staff can record truancy letters (with delivery proof references), parent/guardian contact attempts, and SART meeting notes. Full input validation. Each write audited.
  • Audit logging: Every single read of student data writes an immutable row -- who accessed what, when, from which request, whether it was disclosed to a third party. This is the contract that makes FERPA compliance provable.
  • Weekly reporter: Reads a restricted Google Sheet (intervention evidence) plus Aeries attendance, generates a CSV action report showing which students are ready for referral and which still need evidence. Outputs to local file, Google Drive, or stdout for dry-run.
  • Auth: Google OIDC JWT validation via JWKS in production, with a dev-mode fallback for local testing.
  • Docker deployment: Full dual-database scaffold (MSSQL for Aeries mock + SQLite sidecar), one-shot reporter container, systemd/cron scheduling docs.

39 tests passing. mypy --strict with zero suppressions. Clean linting.

What's Stubbed

Being honest about what hasn't been validated against real systems:

Attendance data is hardcoded in stub mode. Every student lookup currently returns the same fake numbers (90 present, 5 excused, 5 unexcused). The Aeries API adapter is written and unit-tested with mocked HTTP responses, but it has never hit a real Aeries instance. This is the biggest gap.
  • Aeries API connection: The adapter supports retry/backoff, caching, and school-year filtering -- all tested with mocks. But I don't have API credentials from district IT yet. Until those arrive, classification results are meaningless.
  • Google Sheets/Drive integration: Code is complete with header validation against the template. Never run against a real Sheet or uploaded to real Drive. Needs a service account and shared files.
  • MSSQL: All tests use SQLite in-memory. The MSSQL dialect path exists but hasn't been validated on a live SQL Server instance.
  • No edit/delete: Admins can create evidence entries but can't correct mistakes yet. This is a known limitation for MVP.

FERPA-First Design Decisions

Working with K-12 student data means every design choice has a compliance dimension:

  • Pydantic allowlists: All API models use extra="forbid". If a field isn't explicitly in the schema, it can't leak. No accidental PII exposure from overly broad serialization.
  • Report-only pilot: The initial deployment doesn't even run as a web app for staff. A scheduled job reads a restricted Google Sheet and Aeries, drops a CSV into a restricted Drive folder. Minimal access surface.
  • Evidence keying: The Google Sheet uses school_code + student_id only. No student names in the Sheet. No fuzzy matching. Names only appear in the final restricted report output.
  • Audit contract: Every function that reads student data must call write_audit(). This isn't a convention -- it's enforced in code review and tested. The audit log records action type, resource path, processing mode, and third-party disclosure target.

The Stack

  • Backend: Python 3.11, FastAPI, SQLAlchemy (dual engines)
  • PDF: Jinja2 + WeasyPrint
  • Auth: Google OIDC JWT with JWKS verification
  • Google APIs: Sheets (read) + Drive (write) via service account
  • Observability: Prometheus metrics + structured JSON logging with request_id threading
  • Deployment: Docker, systemd timer, cron -- three documented scheduling paths
  • Quality: mypy --strict, ruff, 39 tests, idempotent migrations for SQLite + MSSQL

What's Next

The code is waiting on external dependencies, not more engineering:

  • Get Aeries API credentials from district IT and validate attendance reads against real students
  • Set up Google service account, import the evidence template into a restricted Sheet, run the reporter against real data
  • Pilot with the small SARB admin team (3-4 people) before broadening access
  • Add edit/delete flows for evidence entries

After validation, the product direction is multi-district licensing. Over 1,000 California districts use Aeries, and SARB compliance is a universal pain point. The architecture already isolates by school code and supports configurable API endpoints -- but that's future-state thinking. Right now the goal is: prove it works for one school, with one admin team, against real attendance data.
